agente autónomo · Hermes AgentHermes trabaja solo. El arnés decide cuándo terminó.

Reglas de tu repo que se hacen cumplir solas mientras Hermes trabaja en él — en la CLI, en el gateway y en los cron—, incluidas las dos superficies que Claude Code no tenía: lo que el agente guarda para siempre y lo que corre sin nadie mirando. Encima, un loop que le da tareas, lo deja verde o lo para cuando se traba, y un panel donde lo ves trabajar.

01tesis

  

    
Un agente que aprende repite sus errores con disciplina

    
Hermes escribe su propia memoria, crea y parchea skills, y corre tareas programadas en Telegram, Slack o un cron. Eso lo vuelve útil, y también vuelve permanente cualquier cosa que aprenda mal.

    
Un secreto que Hermes guarda en MEMORY.md no se filtra una vez: entra al prompt de cada sesión futura, en cada plataforma. Una skill que enseña a usar --no-verify no apaga un freno hoy: lo apaga cada vez que alguien la cargue. Y en un cron no hay humano para aprobar el comando peligroso: lo que la tarea puede hacer se decide cuando se crea, o no se decide.

    
Este arnés pone frenos en esos lugares además de en la terminal y los archivos, y define "terminado" con un gate: no por lo que el agente dice, sino por lo que un comando imprime. Es el hermano de agent-harness (hecho para Claude Code), rehecho sobre el modelo de extensión de Hermes y verificado contra su código, no contra su documentación.

  






  
02autonomía

  

    

      
Autonomía es un loop con salida, tope y freno de mano

      
Un agente autónomo no es un modelo bueno: es un modelo metido en lazos de control bien hechos. El arnés gobierna el turno; el loop gobierna la tarea; el panel deja ver los dos.

    

    
    

      
scripts/loop.py
El loop autónomo
Toma la próxima tarea de .hermes/loop/tasks.md, se la da a Hermes y corre el gate. La salida es el gate, no lo que el agente dice. El mismo rojo dos veces seguidas escala (P16 hecho mecanismo). Nunca empuja: lo verde queda en una rama.
falla: un agente que reintenta a ciegas, o que se declara terminado solo

      
scripts/cli.py
La CLI que prueba antes de escribir
rule add pasa la regla nueva por el mismo camino que el plugin: el ejemplo frena, ningún inocente ni el gate quedan frenados, el config pasa el lint. Recién entonces, con --apply, la escribe.
falla: una regla editada a mano que frena el gate y deja al loop sin salida

      
scripts/panel.py
El panel en vivo
Gate, loop, tareas, frenos y cada evento —bloqueo, escalada, lint, gate— en el momento en que pasa. http.server y Server-Sent Events, sólo en 127.0.0.1, sin dependencias.
falla: lo que el arnés frena sólo se ve dentro del chat que lo provocó

      
docs/workshop/
El workshop
Tres horas y media en un sandbox propio, con un agente de juguete determinista (sin API key): guías, frenos, gate, el loop que llega a verde, el que escala, el panel y de un incidente a una regla.
falla: un arnés que sólo entiende quien lo escribió

04onboarding

  

    

      
De cero a un agente autónomo, en ocho pasos

      
Cada paso dice qué tiene que salir. Si no sale, el tablero de problemas tiene la causa: cada fila es un tropiezo real.

    

    
    
      
  1. Requisitos
    Python ≥ 3.11, git y Hermes Agent. En Windows, la terminal de Git for Windows o WSL2 (y sin el alias de python3 de la Microsoft Store).
    
        python3 --version && git --version && hermes --version
    2. 
      
  2. Instalar Hermes
    Con el instalador oficial. Bajá el script y leelo antes de correrlo: es la misma regla que el arnés le aplica al agente.
    
        hermes doctor   # → sin errores rojos
    3. 
      
  3. Traer el arnés y ver el gate verde
    Tiene que terminar en GATE VERDE — 8 señales (o con 2 omitidas si Hermes no está en el PATH).
    
        git clone https://github.com/raalzate/hermes-autopilot.git
cd hermes-autopilot && python3 scripts/gate.py
    4. 
      
  4. Instalar en tu repo, primero en seco
    Sin --apply sólo muestra la lista. + es nuevo, = ya existía y no se toca: nunca sobreescribe.
    
        python3 scripts/install.py ~/code/mi-repo --profile python
python3 scripts/install.py ~/code/mi-repo --profile python --apply
    5. 
      
  5. Conectarlo a Hermes (lo hace el humano)
    El instalador no toca tu config.yaml: qué frenos existen lo decidís vos.
    
        cd ~/code/mi-repo
python3 .hermes/harness/scripts/githooks.py install
hermes skills trust .
python3 .hermes/harness/scripts/install.py . --link-plugin --apply
hermes plugins enable repo-harness
    6. 
      
  6. Verificar que quedó vivo
    doctor.py encuentra el "instalado y muerto": plugin sin habilitar, skills sin confiar, un .hermes.md que tapa a AGENTS.md, secretos ya guardados en la memoria.
    
        python3 .hermes/harness/scripts/gate.py
python3 .hermes/harness/scripts/doctor.py      # → 0 rojo(s)
    7. 
      
  7. La prueba de humo con el agente
    Pedile a Hermes un git reset --hard, escribir en .env y guardar una key en su memoria: las tres tienen que frenar con el motivo. Después /harness para ver los frenos activos. Y desde ahí, las reglas de tu repo se escriben con tus incidentes (/lesson, /new-guardrail) o con cli.py rule add, que las prueba antes de escribirlas.
    8. 
      
  8. Dejarlo trabajar solo
    Una tarea chica que el gate pueda verificar, el loop y el panel en otra pestaña. Tiene que salir ✓ VERDE — gate verde en el intento N o ✗ ESCALAR con el motivo.
    
        python3 .hermes/harness/scripts/cli.py panel     # http://127.0.0.1:8765
python3 .hermes/harness/scripts/cli.py task add "…"
python3 .hermes/harness/scripts/cli.py loop --apply
    9.

05piezas

  

    

      
Seis piezas, cada una contra una falla concreta

    

    

      
plugin/
El plugin repo-harness
Frena en pre_tool_call la terminal, la escritura (incluido el patch V4A), la memoria, las skills y los cron. Corre en proceso: una llamada de función por herramienta, no un proceso.
falla: el agente hace lo que la regla en prosa decía que no

      
.hermes/harness.config.json
Un solo archivo de reglas
Reglas, rutas y hasta los nombres de las herramientas de Hermes. Cada regla trae su example: el self-test lo pasa por el plugin y es rojo si no frena.
falla: reglas cableadas en el código que nadie se anima a tocar

      
scripts/gate.py
El gate
La única definición de "terminado", declarativa, igual en CI. pre_verify no deja cerrar el turno con código editado y el gate pendiente.
falla: "listo" dicho por el agente, no impreso por un comando

      
regla CONTEXTO
El lint que conoce el escáner de Hermes
Si una línea de AGENTS.md parece inyección, Hermes descarta el archivo entero. El lint te dice la línea antes de que pase, y el tope de 20 000 caracteres antes de que trunque.
falla: el agente arranca sin reglas y nadie se entera

      
.hermes/skills/
Seis skills
/gate, /lesson, /new-guardrail, /harness-audit, /harness-review (el revisor, vía delegate_task) y /harness-port.
falla: el método vive en la cabeza de quien lo inventó

      
doctor · e2e · mutaciones
Los sensores del propio arnés
doctor.py mira tu máquina; hermes_e2e.py corre cada ejemplo dentro de Hermes; mutations.py prueba que el self-test muerde.
falla: instalado y muerto

    

  






  
06freno

  

    

      
Editás JSON. El agente lee el motivo.

      
El reason es lo único que el agente ve cuando lo frenás. Es la diferencia entre que entienda y que reintente con otra forma.

    

    

      
      
    

    
Y el example más cada moreExamples se prueban solos: en el self-test contra el plugin, y en el e2e contra el despacho real de Hermes. Una regla sin ejemplo no entra.

  






  
07contrato

  

    

      
Lo que Hermes promete, leído en su código

      
La diferencia que más importa: en Hermes, un pre_tool_call que lanza una excepción bloquea la herramienta. Un arnés con un bug no "deja de frenar": frena todo. Por eso ningún callback del plugin lanza, y el self-test lo prueba con un freno que divide por cero.

    

    

      
NecesidadPunto de HermesContrato

      
        
frenar una herramientapre_tool_call{"action":"block","message"} — sin mensaje, Hermes lo ignora

        
pedir aprobación humanapre_tool_call{"action":"approve"} → el gate de aprobación de Hermes; en cron se niega solo

        
no cerrar con el gate pendientepre_verify{"action":"continue","message"}, sólo si el turno editó archivos, máx. 3

        
lint del archivo recién escritotransform_tool_resultel primer str reemplaza el resultado que ve el modelo

        
estado del repo al abrirregister_system_prompt_section≤ 4000 caracteres, congelada por sesión

        
pistas según el pedidopre_llm_call{"context"} se suma al mensaje del usuario

        
el directorio correcto_authoritative_workspace_rootel cwd de la sesión, no el del proceso (gateway, cron, Desktop)

      
    

  






  
08aprende

  

    

      
Lo aprendido pasa por los mismos frenos que lo ejecutado

      
Tres familias de frenos que un arnés para Claude Code no necesitaba.

    

    

      
memory
La memoria
Filtra secretos y "reglas" que contradicen a un freno. Mira sólo lo que se guarda: sacar un secreto que ya estaba tiene que poder hacerse. doctor.py encuentra lo que se guardó antes de instalar el arnés.

      
skill_manage
Las skills
Una skill que enseña un paso prohibido es un freno apagado en todas las sesiones que la carguen. Se le aplica terminal.deny a lo que escribe, dentro de operations[].

      
cronjob_manage
Lo desatendido
Sin humano, la aprobación no tiene a quién preguntar. El freno decide al crear: nada que publique, y un intervalo mínimo (entiende 30s, listas y rangos de cron).

    

  






  
09cicatrices

  

    
Lo que costó aprenderlo

    
Cada una terminó en un mecanismo (y en docs/gotchas.md), no en una advertencia.

    
El plugin pasaba el self-test y en Hermes no importaba
Causa: Hermes copia el directorio del plugin para validarlo e instalarlo; el núcleo vivía afuera. Mecanismo: núcleo dentro del plugin, self-test que carga desde una copia, y hermes plugins doctor en el gate.

    
Un patch en modo V4A se salteaba los frenos de escritura
Causa: ese modo no trae path; las rutas van en encabezados dentro del texto. Mecanismo: la gramática V4A va al config; el freno evalúa cada ruta y cada línea agregada.

    
El arnés se apagaba en el gateway y en cron
Causa: buscaba el repo desde el cwd del proceso, no desde el de la sesión. Mecanismo: el plugin le pregunta a Hermes el cwd de la sesión; caso en el e2e con el proceso afuera y la sesión adentro.

    
En Windows el gate no fallaba: desaparecía
Causa: consola cp1252; imprimir ✓ reventaba antes de verificar nada. Mecanismo: salida UTF-8 forzada y un caso del self-test que emula cp1252 — lo cazó la matriz de CI.

13límites

  

    
Lo que este arnés todavía no hace

    
La terminal escribe archivos de muchas formas: el freno ve las redirecciones (>, tee), no un cp ni un python -c. Para eso está el pre-commit, que no deja entrar lo protegido al historial.

    
Los patrones del escáner de inyección de Hermes están copiados a mano en el config: si Hermes suma uno, el lint no lo sabe hasta que alguien lo copie.

    
El loop trabaja una tarea por vez, en una rama: todavía no reparte tareas en paralelo (worktrees).

    
El sensor inferencial (harness-review) no tiene prueba de vida con tasa de acierto: lo que el gate no puede verificar sigue siendo juicio sin medir.

    
El loop es tan bueno como el gate que lo cierra: si las pruebas del repo no prueban nada, el verde no significa nada.
